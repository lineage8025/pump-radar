## 一、策略本體只有 77 行

`src/grid.js` 三個純函式即全部策略，其餘 8,000 行都是接交易所 / 對帳 / 續跑的水電工。

### 1. 鋪格（`buildGrid`，grid.js:9）

```
spacing   = (upper - lower) / gridCount
levels[i] = lower + i * spacing            i = 0..gridCount
```

**等差網格**，無等比選項。`levels` 長度 = gridCount + 1。

### 2. 初始鋪單（`seedOrders`，grid.js:34）

現價下方掛買、上方掛賣；距現價 `0.25 × spacing` 以內的格位跳過（避免開機即吃市價）。
三種模式差在「哪一邊允許開倉」：

| 模式 | 下方買單 | 上方賣單 | 適用 |
|---|---|---|---|
| `neutral` | 開多 | 開空 | 橫盤震盪 |
| `long` | 開多 | **reduce-only**（只平多） | 震盪偏漲 |
| `short` | **reduce-only**（只平空） | 開空 | 震盪偏跌 |

`isReduceOnly(side, mode)`（grid.js:19）就是這張表的程式化。

### 3. 成交後補單（`replacementFor`，grid.js:59）—— 唯一的狀態轉移

```
買單於 level i 成交  →  於 level i+1 掛賣單     （i+1 > gridCount 則不補）
賣單於 level i 成交  →  於 level i-1 掛買單     （i-1 < 0 則不補）
```

一買一賣走完一輪，賺 `spacing × sizeBase`。**整個網格就是這條規則自我驅動**，沒有別的觸發源。

## 二、四個不變式（真正的價值所在）

策略是 trivial 的，會爆的都在狀態管理。以下每條都附「違反會怎樣」——這是原專案註解裡記錄的實戰教訓。

### ① 一格最多一張掛單（bot.js:424-426）

```js
if (this._pendingLevels.has(lvl)) return;                        // 飛行中的下單
for (const a of this.active.values()) if (a.levelIndex === lvl) return;
```

**違反後果**：「補到 i+1」會跟「i+1 上本來就有的單」疊起來，掛單數隨時間單調爬升，
保證金被無謂佔用，最終下單被拒。對帳時額外撤掉重複單（bot.js:849）收斂回一格一單。

註記：`_pendingLevels` 是**飛行中**的去重（下單 request 已送出但尚未回 orderId），
少了它在高頻成交時會漏判。

### ② 對帳絕不重新鋪開倉單（bot.js:854-860）—— 最致命的一條

原註解直譯：

> 對帳不再重新鋪開倉單。透過 seedOrders 重鋪會在剛剛被成交（正確地）清空的格位
> 重開一張**同向**單——它的止盈腿在隔壁一格，不在原地——這讓網格單向無限開倉（庫存失控）。
> 網格只由「成交 → 補反向腿」的鏈維持。對帳只負責 prune（保持追蹤準確）與 trim（一格一單），
> **永不開新倉**。

**違反後果**：單向庫存無限累積 → 爆倉。這是網格 bot 最經典的死法。

### ③ 開倉腿 / 平倉腿必須分開對待（bot.js:418、bot.js:455）

- 保證金不足觸發 backoff（60s 暫停補單）時，**只擋開倉腿**：
  `if (opening && !o.recovery && Date.now() < this._refillPausedUntil) return;`
- 下單失敗的重試佇列**只收平倉腿**，開倉腿設計上不重試：
  `if (o.opening !== false && !o.reduceOnly && !o.recovery) return;`

**違反後果**：丟掉一張止盈（reduce-only）單，那份庫存就**永遠沒有出口**——
因為補單只在成交事件觸發，沒有第二次機會。平倉腿永不增加曝險，重試永遠安全。

### ④ 成交必須「正面確認」（extended.js:405-457）

「訂單從掛單列表消失」**≠** 成交。可能是被撤、被拒、或 API 抽風。
原實作去 order history 查 `filledQty`／終態 status：

- `filledQty > 0` 或 status 含 FILLED → 判定成交（並用**實際成交量與均價**回報，非原始委託量）
- status 含 CANCELLED/REJECTED/EXPIRED → 判定未成交
- status 仍是 NEW/OPEN/PARTIAL → **掛單列表那筆「消失」是 API 假象**，恢復追蹤
- 查不到 → 重試最多 12 輪，仍不確定則**當作未成交、不補單**

**違反後果不對稱**：誤判成交 → 補一張反向單 → 憑空開出一個裸倉。
所以預設必須偏向「不確定就當沒成交」。

## 三、損益結構的數學

```
最大庫存    = gridCount × sizeBase                      （價格穿透整個區間時）
所需保證金  = gridCount × sizeBase × mid / leverage      （bot.js:398-409 原樣）
每格淨利    = spacing × sizeBase − 往返手續費
出區間虧損  = 最大庫存 × |邊界 − 現價|                    ← 無上限
```

損益形狀是「**小賺很多次 + 偶爾大虧一次**」。

> **⚠ 這與 crypto-pulse DirProbe 的教訓同構：高勝率完全不保證正期望。**
> 網格的勝率天然接近 100%（每格都賺），但期望值由「穿出區間的頻率 × 穿出後的幅度」決定。
> 任何網格研究若以勝率或完成格數為指標，等同沒有驗證。**頭條指標必須是淨損益分佈。**

### 手續費與展示口徑的坑（原專案的缺陷，抄的時候要修）

- README 宣稱「格距必須大於手續費，啟動時強制校驗」，實際 bot.js:254 **只警告不阻擋**。
- `theoreticalProfit` = 累加 `spacing × fillSize`，**完全不扣手續費**。
- 回收階梯（認賠出場）的成交被 bot.js:488 直接判定為 `closing`，
  於是計入 `completedRungs++` 與 `gridProfit +=` → **虧損出場反而讓「完成格數／理論利潤」上升**。
  頭條 PnL 走交易所回報的 realizedPnl 是準的，但這兩個展示欄位在最需要看清楚時會誤導。

## 四、它沒解決的兩個問題（＝調研的真正標的）

網格的全部風險都塌縮成這兩題，而原專案**兩題都是拍腦袋**：

### Q1. 區間該多寬？

原作法：`trend.js:66` 用 ATR 給一句「建議單格間距不小於 ATR 的一半以覆蓋手續費」，
「智能填充」按 ATR 推區間上下界。**無任何統計依據，未做任何驗證。**

正確問法應是：
> 給定當下的波動狀態，未來 T 小時內價格走出寬度 W 的機率是多少？

這是可以直接用歷史資料量出來的（見 `RND_BACKLOG.md` Phase 0）。

### Q2. 穿出去怎麼辦？

原作法只給兩個選項，**未做任何統計比較**：

| 策略 | 行為 | 風險特性 |
|---|---|---|
| `close` | 撤單 + 市價平倉 + 停止 | 損失確定，但在急跌中 IOC ±5% 可能完全不成交 |
| `recover` | 掛 reduce-only 階梯等回調分批減倉 | 只減不加、**不自動止損**，單邊延續會一直扛 |

註記：`recover` 的「只減不加」由 reduce-only 保證，這點設計是對的——
它不可能把套牢部位越加越大。但它沒有時間止損，趨勢延續即無限期持有。

### 設計矛盾（值得警惕）

`trend.js` 偵測到上升趨勢就推薦 `long` 網格，但 `ai/service.js:225` 的 prompt 自己寫著
「網格的數學本質：震盪市賺錢、單邊市虧錢」。**規則層與 AI 層的假設互相打架**，
說明這套趨勢→模式的映射沒有經過任何一致性檢查。

## 六、工程參考點：AI 該擺在哪裡

原專案 `ai/service.js:3-7` 的設計原則，**這點它做對了，值得直接抄**：

> 1. AI 永遠不進交易快回路——下單/補單/對帳全部保持純規則。
> 2. AI 永遠不直接執行寫操作——只能「提議」，前端彈確認框，由使用者確認後走既有 REST 執行。
> 3. 所有 AI 呼叫失敗均安全降級，不影響交易。

執行面也確實落實：未知 action 一律降級為 none（service.js:304）、交易所代號白名單（:306）、
前端二次 `confirm()`（index.html:1931）、`/api/env` 白名單擋掉所有交易密鑰（server.js:354）。

**採納這個分層的理由不是「AI 不夠聰明」，是可驗證性：**

| 層 | 適合 | 理由 |
|---|---|---|
| 下單 / 補單 / 對帳 | 純規則 | 必須能回放重現、能單元測試、失敗模式可窮舉 |
| 參數選擇（區間 / 格數） | 統計模型 | 要能算出樣本內基準與 forward 成績 |
| 敘述 / 告警 / 日報 | LLM | 錯了只是話講得不對，無資金後果 |

> **LLM 決策天然不可預登記**：同樣輸入下次給不同答案，永遠算不出樣本內基準，
> 也就永遠無法判定它有沒有 edge。這正是 pump-radar「改任一 PARAMS 值＝v2，需重開預登記」
> 那條紅線在防的事。

## 七、安全性缺陷（若日後參考其架構，這些必須修）

1. **無認證 + 無 CSRF 防護**（server.js 全域）：`readBody()`（server.js:128）不檢查 Content-Type
   直接 `JSON.parse`，且無 Origin/Referer 檢查。使用者本機跑著時，任何瀏覽的網頁都能發
   CORS 簡單請求（`Content-Type: text/plain`，不觸發 preflight）打到 `/api/{ex}/close-position`
   或 `/api/{ex}/stop`——讀不到回應，但**副作用會執行**。
   更嚴重的是 `/api/env` 白名單含 `AI_BASE_URL`，可被改成攻擊者主機，
   下次 AI 呼叫即以 `Authorization: Bearer` 把 `AI_API_KEY` 送出去。
   預設綁 `127.0.0.1`（config.js:96）擋掉區網暴露，但擋不住 CSRF / DNS rebinding。
2. **崩潰重啟自動續跑無人工確認**（server.js:521-541）：上次為 running 即自動接管交易所上
   還掛著的單並繼續交易。斷電後盲目重啟 = 自動恢復實盤下單。
3. **儀表盤依賴 CDN**（index.html:7 拉 cdnjs 的 Chart.js），與「本機離線」的宣稱矛盾。
