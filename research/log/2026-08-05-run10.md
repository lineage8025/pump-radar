## 限制段

1. **`n_trades` 是聚合成交（aggTrades）筆數，不是原始逐筆成交（raw trades）筆數。**
   Binance 的 aggTrades 資料集本身已把「同一時間戳、同一方向、同一價格」的連續成交
   合併成一筆，所以本欄位系統性低於真實成交頻率。這不影響 OHLC 重建（已交叉驗證
   完全吻合），但若 Phase C 要用「成交筆數」推估流動性深度，需注意這個口徑差異。
2. **`n_mid_crossings` 的中價定義是該分鐘事後的 `(high+low)/2`，非事前可觀測量**，
   只能用於事後路徑分析（如 Phase B 重跑 Q8），不能當成即時交易訊號。
3. **1 分鐘聚合仍會抹掉分鐘內的部分路徑細節**（例如同一分鐘內多次觸及同一價位的
   先後順序）。Phase B 若需要比 1m 更細的路徑重建，本摘要不足以支持，須改抓更細
   粒度或直接用逐筆（但逐筆體積過大不可行，見 Phase A 動機段的磁碟限制）。
4. **範圍僅 3 標的 × 3 個月**（`docs/RND_BACKLOG.md` 方向三 Phase A 凍結範圍），
   不覆蓋 Q8/Q10 用到的其餘 7 個標的與更長窗口。Phase B 若要完整重跑 Q8 全部 450 格
   （10 標的），仍需擴大 Q11 的資料涵蓋範圍——這是下一輪的候選工作，非本輪產出。
5. **承襲 `research/program.md` §4 的 Parkinson 漂移偏誤限制**：本管線本身不做振幅
   估計，但其產出將用於 Phase B 的 intrabar 路徑重建，該限制屬於下游分析而非本管線。

## 最強反駁

「你只驗證了 BTC 2024-01 一個月的 15m resample，其餘 8 個標的-月組合完全沒有交叉
驗證，管線可能對其他標的有未發現的 bug（例如某些標的的 aggTrades 欄位格式不同）。」
**回應**：這個反駁成立，是本輪誠實的殘留風險。緩解證據：①`fetch_day` 的 header
偵測邏輯（首欄是否為數字）與 `fetch_klines.py` 沿用同一套已在其他標的驗證過的手法；
②9 個標的-月的覆蓋率報表本身零缺天零缺分鐘，顯示欄位解析未曾整月失敗（若格式不符
會在 `pd.to_numeric` 或 `groupby` 階段直接拋錯，不會靜默產出錯誤但完整的資料）；
③BTC 是流動性最高、微結構最複雜的標的，若管線對 BTC 都能逐 15m 根精確重建，
對流動性更低、tick 更疏的 ETH/SOL 出錯的機制性理由不明顯。**但這不等於已排除**，
下一輪處理 Phase B 前應追加 ETH 或 SOL 至少一個月的同款交叉驗證。
