## 發現

1. **Q15 點名的「最可能的機制」（`BASH_MAX_TIMEOUT_MS=900000` 單指令 15 分鐘超時）
   沒有被本輪找到的證據支持，反而被正面證偽**：
   - 唯二時長吻合 900s 的執行（A 組兩次）根本沒有 Claude session 跑過，是**與
     aggTrades／Bash 完全無關的 GitHub 排程層問題**（`Runner of type hosted` 佇列取不到
     機器，是 GitHub 基礎設施層級的容量／排隊問題，不是本專案程式碼或指令的錯）。
   - 真正對應「骨架日誌後中斷」現象的 7 次執行（B 組），Claude session **本身回報成功
     結束**（`is_error:false`），且全部遠遠沒有靠近 900s 或 80 turns 的任何一個上限。
     若真是撞 Bash 900s 超時，該次 Bash 呼叫本身會失敗並在 log 留下錯誤文字、
     session 通常會續跑或帶著錯誤退出，**不會是乾淨的 `success`**。
2. **`permission_denials_count` 不是一致的解釋**：7 次裡 6 次為 0，只有 run14 為 2，
   且 run14／run15 的 `num_turns` 剛好都是 63（但 run14 有 2 次拒絕、run15 沒有），
   兩者無法用同一個因子解釋。
3. **`num_turns` 沒有固定門檻**：32/43/45/45/46/63/63，七個數字分散，不是撞到某個
   隱藏的固定 turn 上限（若是，應該全部停在同一個數字附近）。
4. **本輪目前的 CI log 讀取路徑（`gh api .../jobs/<id>/logs`）只暴露 claude-code-action
   的 `init` 與最終 `result` 兩個事件，中間的逐輪（turn-by-turn）內容沒有輸出到這個
   log 串流**——這是本輪查證能力的**天花板**：能確認 session「乾淨結束但工作沒做完」，
   但無法從這份 log 看到 session 在做什麼、為何在那個時間點自行結束。

## 限制段（`program.md` §4 既有限制，本題不涉及 K 線資料，仍列出以維持格式一致）

本題不使用任何 K 線／振幅資料，**Parkinson 漂移偏誤、去叢集、封存段等既有限制段條目
皆不適用**。本題特有限制：①`gh api` 的 job log 端點只回傳 GH Actions runner 自己
記錄的 stdout（含 claude-code-action 包裝腳本的 print），claude-code-action 本身是否
有更細的逐輪 log 存在別處（例如 workflow artifact、Anthropic 後台的 session 記錄）本輪
未查證，不能排除；②樣本僅 7 次（全部可查證的 Q11 skeleton-only 執行），n 不大，
`num_turns`／`duration_ms` 的離散模式描述性而非統計檢定；③兩次 GH `failure` 的
annotation 文字本身是 GitHub 產品呈現給使用者的訊息，其背後真正的基礎設施原因
（容量不足／區域性中斷／其他）本輪未進一步查證，只確認了「與本專案程式碼無關」
這一點。

## 最強反駁

「7 次 `is_error:false` 且時長遠低於 900s，不代表沒有撞到某種超時——也可能是
`timeout-minutes: 90` 的 job 層級上限的**某個更早階段**（例如 setup steps）
先吃掉了大部分時間，讓 claude-code-action 自己只分到 5~8 分鐘就被上層的某個機制
（而非 `BASH_MAX_TIMEOUT_MS`）提前結束，只是這個結束方式恰好被 SDK 包裝成
`is_error:false` 的『乾淨』結果。」——**本輪無法排除這個反駁**：`duration_ms` 只是
claude-code-action 這一個 step 自己回報的內部耗時，我沒有查證這個 step 在
job 的 90 分鐘總預算裡實際佔用了多久牆鐘時間、也沒有查證 job 其餘 steps
（checkout／setup-python／guard 等）分別花了多久。若上層有一個比 900s 更短、
對 agent 不可見的軟性中止機制在起作用，那才是真正的機制，而本輪只證明了
「不是 `BASH_MAX_TIMEOUT_MS`」，沒有找到「是什麼」。
